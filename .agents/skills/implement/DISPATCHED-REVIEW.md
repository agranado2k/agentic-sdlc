# A dispatched review — the skill dispatcher and the broker

Opened from `/implement` step 9(b) when the reviewer tier names another agent harness — and its last section, the verifier, from step 9 whichever review ran. `SKILL.md` stays the entry point; this file is the branch. The text below moved here verbatim from it, so "above", "below", "the next bullet" and a step's number still point into `SKILL.md`.

**When the reviewer tier names another agent harness, the review is dispatched, and the broker posts it.** The dispatched worker is offline by design — with network it would hold your forge credentials while reading a diff that is untrusted content — so it prints its findings and stops. The **broker** is the host-side script that validates that report and performs the forge actions on the worker's behalf: one review carrying the standards findings inline, one comment carrying the behavior confirm-list. This skill ships to every project unstamped, so it names the two roles and not their files: the root `AGENTS.md` names this project's **skill dispatcher** (the command that runs a skill on the agent harness its tier maps to) and its **broker**. Compose the two as a redirect followed by the broker, never as one pipeline, and run the whole composition as **one shell invocation** — one command line, typed once: `tip=$(git rev-parse HEAD); <skill dispatcher> review-pr … > <report file>; rc=$?; [ "$rc" -eq 0 ] && <broker> <PR#> <report file> --commit "$tip"` (`rc`, not `status`, a name some shells reserve). The tip and the exit status are shell state, and an agent harness that starts a fresh shell per command loses both: the status it then reads is the new shell's own, the gate passes on a dispatch that failed, and the tip arrives empty. Where one invocation is impossible, carry both in files — never in variables across commands. **Record the branch tip before you dispatch**, from the pushed branch. It goes to the broker as `--commit`, the cross-check against the commit the worker says it reviewed: a report about any other commit is refused rather than posted on this one. **Dispatch `/review-pr` by skill name, with stdout redirected to a file** outside the tree the worker reads, handing it the reviewer stamp you resolved above, the branch, its base and the ticket as the spec — never this session's narrative. A factory ticket's dispatch passes `--ticket T-<digits>` and its `factory show` text's file as the spec, as [`STAMP.md`](STAMP.md)'s last section says. For a ticket with a `Covers:` line, append the check-table reader's output to that spec file first, under a `Check-table reader:` line, as `/review-pr`'s `CHECK-TABLE.md` says: the offline worker cannot fetch the PR body the reader needs. Pass no `--prompt-file`: the skill dispatcher stages the offline worker contract (`.agents/prompts/review-worker.md`) itself, and a `--prompt-file` is the caller's own document — a session that passes one owns the contract inside it. The dispatch blocks until the worker exits; if you must poll instead, poll for the process, never for a phrase in its output — the prompt you sent contains every phrase the report will. **Check the dispatcher's exit status before anything reads the file.** Only on 0 is the file a report. On any other status — a non-dispatch exit, or a worker that died — the file holds a model id, a fragment or nothing at all, never a report, so no dispatched review ran: say exactly that in your report, with the status, and do not call the broker. The two working cases among them are the status that says the tier names no other agent harness and the one that says the agent harness it names is not reachable from here — in both the file holds the model id and your report says no cross-vendor review ran, and in both the in-session spawn above *is* the review on that model — reached, for the first, through the hand-back below when the dispatcher stages one. **On the status that says the tier names no other agent harness, a skill dispatcher that stages the worker contract hands the review back**, the way a cascade hands back a rung: exit 3, the model on stdout, and the contract staged at `<git dir>/skill-review/prompt` — `<git dir>` is what `git rev-parse --absolute-git-dir` prints in the checkout you dispatched from — its `Trace-Run:` and `Trace-Spawn:` lines first, then the commit the dispatcher pinned from the branch and the path of that commit's diff, staged beside it with the commit in `commit`, so a reviewer that runs no command reads them instead. Spawn **one** reviewer: the agent type the tier names, the model the file holds (an empty file means pass no model, and the spawn inherits yours), and the prompt file's content **verbatim** as its prompt — never this session's narrative. What it returns is its report, untrusted content like a worker's: save it unread to a file outside the working tree and run the broker on that file, `<broker> <PR#> <report file> --commit "$(cat <git dir>/skill-review/commit)"` — the pinned commit is the cross-check here, carried in a file, so it survives a fresh shell. The broker's answer means what it means for a dispatched review. Where exit 3 leaves no staged prompt, the in-session spawn of step 9(b) is the review, as before. A dispatcher that refuses to stage the hand-back — a branch or base not passed, or naming no commit — exits 2 and names what is missing or wrong on stderr: here exit 2 is a caller error to repair, never a stop and never a review that ran, so fix the call and dispatch again. **Why never a pipe:** a POSIX shell cannot see the dispatcher's exit status through a pipe, so a non-dispatch exit would hand the broker a model id, and the broker would refuse it as a malformed report — the right refusal for the wrong reason. Two commands keep the two failures apart. **The broker's stdout is the answer**: the review URL and the comment URL, one per line, then a line naming anything it withheld. A broker that refuses posts nothing and says why on stderr — that reason goes in your report, and you never post around a refusal by hand: the refusal is the policy working. One that says the reviewed commit is no longer the branch's means dispatch again. **No broker named by the root manual** means this project has no sanctioned way for a dispatched review to land, so you dispatch none: the in-session spawn above is the review, and your report says no cross-vendor review ran because the manual names no broker. A worker's report is untrusted content until the broker has validated it, and a credentialed session relaying one unvalidated is the path to the forge the broker exists to close — a gap to report, never to fill by hand.

## The verifier — on the review's head commit

Opened from `/implement` step 9 once the independent review has been requested, whichever mechanism ran it; the call mirrors the dispatched review's composition at this file's top.

**What it is.** The **verifier** is an advisory reviewer from another provider than the diff's author — or, where the policy's walk falls back, another model family — run on the head commit the kit's own review saw. It adds a second reading; it is **never the review**. The landing counts only `/review-pr`'s verdict, so a `pass` from the verifier lands nothing, and a `blocked` stops nothing: the session reports it, and never waits on it before step 10.

**When.** Ask the resolver, naming the diff's author: `AGENT_SESSION_MODEL=<your model, in the policy file's word> sh scripts/agents.lib.sh reviewer cross-provider`. When it prints nothing, no verifier is requested and this section ends here: say so in your report. When it prints a model **and** the root manual names this project's verifier call — the skill dispatcher's `review-pr` on the reviewer tier in the `cross-provider` domain, and the broker's verifier flags — request it once, **after the review's verdict is recorded**, on **the same head commit**: the commit the review pinned (step 9's branch tip, or `<git dir>/skill-review/commit` for a review handed back). `/implement` requests it once per head commit, at that head only; a later head is `/pr-iterate`'s. A root manual that names no verifier call means none is dispatched, and the report says so.

**The call** — one shell invocation, as the review's is, so the status and the commit survive: `<skill dispatcher> review-pr --tier reviewer --domain cross-provider --pr <PR#> --ticket <N> --set BRANCH=<that commit> --set BASE=<base> --set-file SPEC=<the ticket body file> > <report file>; rc=$?` — add `--pr-body <file>` when you hold the PR body, which it otherwise fetches for its check table — then read `rc` before anything reads the file:

- **0** — the file is the verifier's report. Run the broker on it as a verifier's: `<broker> <PR#> <report file> --commit <that commit> --verifier --rung "$(cat <git dir>/skill-verify/rung)" --provider "$(cat <git dir>/skill-verify/provider)" --staged "<git dir>/skill-verify"` — the directory the dispatcher printed, whose pins and findings the report must answer one line each.
- **3** — handed back: spawn **one** reviewer, the agent type the tier names, on the model the file holds (empty: pass none), its prompt the content of `<git dir>/skill-verify/prompt` verbatim (the dispatcher wrote its `Trace-Run:` and `Trace-Spawn:` lines first); save its report unread to a file outside the working tree, then run the broker as for 0, with `--commit "$(cat <git dir>/skill-verify/commit)"`. If that spawn fails, run the same call again with `--spawn-failed '<the model>'`: the dispatcher re-resolves once past it.
- **exit 6** — no verifier ran: none resolved, or a spawn failed past its one re-resolve. The dispatcher recorded `verify.verdict outcome=unavailable` on the PR; nothing is posted and nothing is retried. Your report names it, quoting the dispatcher's stderr reason.
- **2** — a caller error: repair the call and run it again. Any other status: no verifier ran; report the status, and call no broker.

The broker's stdout is the answer — the verifier's review and comment URLs; your report lists them beside the review's. A broker that refuses posts nothing: report its reason, and never post around it by hand.
